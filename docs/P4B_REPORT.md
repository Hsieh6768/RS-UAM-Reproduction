## 调用与跨批状态

```python
from random import Random
from src.common.config import load_config
from src.m4 import M4Config, M4HALNS

config = M4Config.from_config(load_config("configs/base.yaml"))
solver = M4HALNS(road, config)
out = solver.solve(snapshot, plans_by_request, sparse, rng=Random(101))
# 调用方确认并提交 out.best_solution 后，取得下一批快照和 M3 结果
later = solver.solve(next_snapshot, next_plans, next_sparse,
                     previous=out.state, rng=Random())
```

`out` 提供同批次的 `safe_baseline`、`current_solution`、`best_solution`、生效配置、初始评分、候选和分量统计、两种计时、验证耗时及可传递状态。直接用 `M4Config(noD=True)`、`M4Config(noA=True)`、`M4Config(noS=True)` 可分别启用三种消融。正式数据及 P0 清单均未改写。

- 首批的安全解 S0 由 P4-A 的完整解码器核查快照、预约和冻结承诺。在已有外部剩余请求序列时，可向 `solve` 直接传入 `remaining_sequence`。
- 跨批状态保存七个评分、显式 RNG 的状态、最佳方案和资源绑定、按全局顺序排列的稳定 Task ID、路网版本和批次时刻。下一批从当时的 Type3 快照中过滤出仍待执行的正式任务，逐请求校验数量、身份、次序及承诺，再交给 P4-A 恢复基础解。传入 `previous` 时会将提供的 RNG 恢复到该状态。状态只适用于同一仿真轨迹及其实际采用的方案。
- 已完成接客、正在飞行的航段、步行均不重新占据正式位置。有固定方案但没有待排正式任务的乘客，仍保留实际服务链、预计终点时刻与评分。上一批分数不会进入本批比较。
- `BaselineOrderRequired`、`SnapshotError` 与独立验收错误向调用方传播，失败记录默认写入 `outputs/p4b_failures/`。超时单独处理。当前阶段没有调用整批提交器或改动 P1 事件队列。

## 算子、退火和预算

PAPER §5.3.1、§5.3.4–5.3.5、Algorithm 4、Table 3–4 与 DECISION D005–D007。S1 取各请求第一方案、随机绑定资源，可作为合法的初始 current。best 在 S0、合法 S1 及所有已完成的后续候选中单调更新，平分保留先前最佳。目标沿用 §4.2 式 (2)，以原始请求时刻至最终完成的浮点分钟计费。

| 算子 | 候选上的操作 |
|---|---|
| p_exchange | 对可切换的普通请求随机选择其他可绑定方案并重新选资源。任务数变化时随机调整出现位置，保留其他请求间次序。 |
| v_exchange | 在同一方案的候选资源组合中更换绑定。 |
| restart | 回到本批仍然有效的请求全集；Type3 保留既定方案与资源，普通请求随机选可用方案、资源和出现顺序。 |
| insert | 每个片段抽一项重新插入，按 D007 排除直接抽取 Type3。 |
| cut | 每个片段把两个位置界定的闭区间按原顺序移到末尾。 |
| swap | 每个片段交换两个选中位置。 |
| reverse | 每个片段反转两个选中位置间的闭区间。 |

编号经重排后按各请求在新序列中的出现次序映射为正式任务。Table 3 的顺序算子每次处理所有片段。noD 使用完整第二层和 `FullDecoder`。noA 均匀选择并固定权重。noS 接受改善或平分，拒绝降分。

外层开始存下 `vold = best.v`，按正权重轮盘选一个算子并连续运行内层。结合 Algorithm 4 第 7 行与 §5.3.5 的 current 表述，只有**完整外层结束的 current.v 大于 vold**才给所选算子加 θ=0.1。随后按式 (24) 对七项各自抽取一次概率，低于 ψ=0.4 时加均匀扰动 ±0.02，下界为 1e-9。中途超时的外层没有完整区块奖励。所有抽样均使用调用方的 RNG。

D007 最大化 SA 对合法的非降分候选直接接受，对降分按 `exp((vnew − vcurrent) / T)` 接受。温度降至零时仅接受非降分。默认 T0=70|R|，每次完成内层尝试即乘 0.7（含不可行候选）。外层上限为 2|R|，内层为 25 次。独立评分、最优解、当前解和温度的选择均限定在同一个批次。

D014 墙钟从 `solve` 入口开始，覆盖继承状态的核对、S0、S1、图、算子、完整或分量试算与修复、退火、评分及最终选择。默认 `perf_counter` 10 s，大规模模板 30 s，同时记录 `process_time`。CPU 诊断需要 CPU 限额与独立墙钟保险，现有配置为 10/30 s。可注入两种时钟。以 S0 开始时尚无可返回的本批结果，因此允许完成必要的 S0 恢复并记录实际超时。候选在开始及解码循环中检查截止，半成品不能更新 current 或 best。以较早完成的合法 best 返回。两种超时幅度分别计量。按批汇总提供均值、线性插值 p95/p99、最大值与超时率。

短窗配置只在批次最终方案上调用独立 `ScheduleValidator`；五小时及 48 小时配置默认关闭。该次验证单独计时。P3 和 M5 位于 `solve` 外。论文 §6.2 的 10/30 s 指整批系统求解；本项目按 D014 实施 M4 限额。正式负载下的整批耗时与超时率须由以后手动实验测量。

## 任务图、物理试算与修复

PAPER §5.3.2–5.3.3、式 (22a–b)/(23a–b)、Fig. 5–6、Theorem 1/Lemma 1；DECISION D002–D006。每个节点是 P1 的待执行正式 Task。相邻同车停靠之间建有向顺序边，相邻同请求正式任务之间建有向先后边，同一班次的乘客任务两两建立双向容量边。只在求弱连通分量时忽略边方向；车辆和乘客的时间传播保留原方向。同班次两个乘客可以同时登机。

分量记录已排序的请求 ID 元组作为身份，以及原编码位置和稳定 Task ID。正常建图按任务在全编码中首次出现的位置给分量排序。没有待排正式任务的 Type3 单独保留服务链上下文。分量从同一冻结快照读取历史、预约和资源，以各自的车辆临时队列、既有预订和乘客游标解码。P4-A 的物理计算提取成两种路径共用的内核，接客、下客、航班及步行原算法沿用。结果按原全局位置恢复；未参与试算的车辆保留既定目的地，未参与的航班保留原预订。以恢复后的全部完成时间统一计算目标，避免分片浮点求和次序影响分数。

每个分量返回首个冲突或局部调度。全局首先按请求 ID 比较初始历史/步行传播冲突，其次按原编码中触发冲突的正式任务位置比较，复现 P4-A 的首冲突选择。若为 Type1/2，移除整份分配与全部出现项，仅重建其原分量；桥接请求被删除后，一个分量可变为多个。其他分量的合法结果可继续使用。Type3 冲突使整份候选失效。缓存限于同一 FullDecoder 上的相邻候选，键包含预约回放模式、请求及方案/资源选择、正式 Task ID 顺序。相同任务身份、更换方案时间窗时必须重新计算。

历史顺序的跨批验收单列于 `test_carry_forward_critical_order_then_remove_only_executed_task`。A、B 各四人共享一车，B 最迟 2 s 接客。缺少上一轮顺序且无法恢复基线时抛出 `BaselineOrderRequired` 并保存 FAILED 快照。给出 BBAA 后，B 在 5 s、A 在 15 s 完成。下一快照位于道路边中，已执行 B 的接客，继承序列只剩 BAA；车从当前边结束的 5 s 接续。人为截去一个仍待执行 Task ID 也会显式报错并留证。

**修复顺序的影响。** 四座航班锁定 H 的两席，A、B 各需两席，B 的后续车辆无法沿有向路抵达。编码 BBBHA 先发现 B 的车辆冲突，最终保留 H、A；BHABB 先发现 A 的航班容量冲突，随后 B 也被整单删除，最终仅有 H。两个固定输入分别在完整/分解路径产生相同的逐次修复与座位表，最终都通过独立验证。此例说明候选中先被删除的请求需要通过后续搜索重新加入。另对局部结果注入缺失、重复、额外任务和缺失乘客完成记录，四例均由常开合并检查报错并留下 FAILED 快照。
