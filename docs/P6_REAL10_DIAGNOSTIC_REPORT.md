1. `M4HALNS.solve → FullDecoder.__init__ → prepare_baseline/_decode` 每批从固定任务和时间约定重建 S0。S0 计入预算，搜索外层上限随活跃请求数增长。S1 或 restart 从已批准的候选集选资源，很多安排在具体道路与接客窗口上冲突。独立 ScheduleValidator 在预算计时结束后仅验证最终解。正式 1054 行没有分列 S0、S1 编码、算子生成和物理解码的秒数，无法把外层调用减去搜索的差值解释为 S0 时间。
2. `PartitionedDecoder.decode → _local → FullDecoder._physical/_stop` 在真实道路、容量、前段就绪和时间窗上检查。修复删除冲突的普通请求，然后 `TaskGraph.from_tasks` 重建其受影响分量、再次评估；Type3 冲突不能用删除承诺解决。通过的候选由 `_combine` 合并分量，复制每批缓存的基础车辆/航班字典并重建任务顺序。每候选都存在检查和对象构造，不能将一次修复理解为整套仿真世界重跑。
3. 人工 3 节点夹具，仅改变同一组 12 请求、2 辆车的任务交错。各做 12 次分量解码，串行对照 / 集中接客分别修复 0 / 120 次，调用 _local 24 / 144 次，from_tasks 12 / 132 次，cProfile 总包络约 17.55 / 26.49 ms。另一小图 61 候选的单次 solve 用 52.42 ms，其中 evaluate 包络 41.56 ms，分量 decode 40.92 ms。包络时间有嵌套，不相加。这验证了冲突引起重复工作的机制；E10 上每个函数实际占比仍待采样。
4. 道路时间查询命中率全程 99.688%（评价 99.667%），物理路径命中率全程 77.876%（评价 78.775%）。计数来自共享 RoadRouter，覆盖多个模块；单源搜索另走 `shortest_times_from`。高命中率不能给未命中计价，也不能证明 Dijkstra 是主要耗时。CPU/Wall 预热 99.74%，评价 99.82%，开放尾部 99.65%，排空 97.79%；高负载端以计算为主，不能据此定位具体 OS 调度原因。
5. `SearchBudget` 使用 perf_counter 合作式检查；先构建合法 S0，完整评估并通过检查点后才更新解。SA 可接受变差的 current，独立保存本批最佳合法 best；超时时返回已完成结果。当前批与旧批打分严格隔离。943 批触及预算，其正超时幅度均值 2.560 ms、P50 0.237、P95 14.592、P99 57.628、最大 79.250 ms。整批最大超时 10.401 **秒**。程序实现、短图测试及本次终态支持预算与合法性机制；日志未存完整候选序列，无法对每个历史 best 再作穷举证明。
